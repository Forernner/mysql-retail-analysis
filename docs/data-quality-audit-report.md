**数据集**：UCI Online Retail II · 英国在线零售商交易流水（2009-12 ~ 2011-12）
**验收对象**：2 个源文件 → 合并 → 清洗 → 分析底表
**工具**：MySQL 8.0 / Navicat
**报告人**：王自强 ｜ **日期**：2026-09

## 二、验收标准

按**完整性 / 准确性 / 一致性 / 及时性**四个维度设计检查项，每项均定义检查方法、判定依据与处理动作。

| 维度 | 检查目标 | 检查方法 |
|---|---|---|
| 完整性 | 关键字段是否有缺失，缺失是否影响聚合 | 空值计数 + 影响面量化 |
| 准确性 | 是否存在语义异常值（退货、负数量、零/负单价） | 条件计数 + 交叉比对 |
| 一致性 | 多源合并后是否存在重复、口径是否唯一 | 行数对账 + 排序规则对照实验 |
| 及时性 | 数据覆盖区间是否完整、时间是否可比 | 覆盖天数校验 + 同口径对比 |

## 三、检查过程与发现

### 3.1 一致性

#### 发现 1｜两个源文件的时间范围存在重叠

| 文件 | 覆盖区间 |
|---|---|
| 2009-2010 年文件 | 2009-12-01 ~ 2010-12-09 |
| 2010-2011 年文件 | 2010-12-01 ~ 2011-12-09 |

**重叠区间：2010-12-01 ~ 2010-12-09（9 天）**

#### 发现 2｜合并后存在完全重复行 34,335 行（占 3.22%）

| 来源 | 行数 |
|---|---|
| 跨文件重复（重叠 9 天区间） | 22,202 |
| 同一文件内部重复 | 12,133（分为两组：6,865 / 5,268） |
| **合计** | **34,335** |

重复行按月份分布（前五）：**2010-12 = 23,023**；2010-11 = 1,431；2011-11 = 1,368；2010-10 = 849；2011-10 = 773。
跨文件重复的 22,202 行全部集中在 2010-12，与"重叠区间落在 12 月"完全吻合。

**⚠️ 这个问题的隐蔽性**：如果只做汇总层校验（总行数、总金额），**看不出任何异常**——金额看起来完全正常。只有做行数对账才能发现。

**影响量化**：

| 指标 | 不去重 | 去重后 | 差异 |
|---|---|---|---|
| 2010-12 流水金额 | 884,591.89 | 570,422.73 | **虚高 55.08%** |

> **结论**：不去重则 2010 年 12 月销售额被高估一倍以上，其后所有月度、年度、同比对比都会被带偏。

**处理动作**：在清洗环节做全字段去重（`SELECT DISTINCT`）；原始表保留重复行以便追溯问题来源。

#### 发现 3｜同一列在三种排序规则下有三个值

`COUNT(DISTINCT stock_code)` 在合并后原始表上的结果：

| 排序规则 | 结果 | 差异原因 |
|---|---|---|
| `utf8mb4_0900_ai_ci`（默认） | 5,132 | 忽略大小写：`15056BL` 与 `15056bl` 被算作同一商品（此类变体共 172 组） |
| `utf8mb4_bin` | 5,304 | 区分大小写，但为 PAD SPACE：`47503J `（尾部带空格）与 `47503J` 被算作同一 |
| `utf8mb4_0900_bin` | 5,305 | 大小写与尾空格均区分 |

实测还有一个直接证据：商品编码 `47503J `（尾部带一个空格）出现 80 次，而 `47503J`（无空格）仅出现 1 次。

**处理动作**：清洗时对商品编码、商品名、国家统一 `TRIM`；清洗后**三种口径的结果统一为 4,631**（带变体的记录均落在退货、散客、零价类中，被清洗条件一并剔除）。
**报告约定**：后续所有"唯一商品数"均以默认排序规则 `utf8mb4_0900_ai_ci` 为准，并在报表上显式标注。

补充：商品名的空格问题以**尾随空格**为主 —— 合并后全表 213,035 行与 `TRIM` 结果不同，其中尾随空格 211,195 行、前导空格仅 2,624 行。

### 3.2 完整性

#### 发现 4｜客户编号缺失 243,007 行（22.77%）

| 检查项 | 行数 | 占比 |
|---|---|---|
| 客户编号为空 | **243,007** | **22.77%** |
| 商品名为空 | 4,382 | 0.41% |

**业务判定**：客户编号缺失的记录无法归集到客户维度，会直接污染复购率、客户分层、留存与同期群等全部客户级指标，并导致分母失真。

**影响量化**：散客（无客户编号）对应流水金额 **3,101,456.18**，占全量金额的 **15.15%**。

**处理动作**：客户级分析中剔除；若需报告总销售额，则**同时给出"含散客 / 不含散客"两种口径**并标注分母定义。

### 3.3 准确性

#### 发现 5｜取消订单与负数量记录是两批不同的数据

| 类别 | 行数 |
|---|---|
| 发票号以 C 开头（退货冲销单） | 19,494 |
| 　其中数量为负 | 19,493 |
| 　**其中数量为正** | **1** |
| 数量 < 0（全部记录） | 22,950 |
| 　**数量 < 0 但发票号不以 C 开头** | **3,457** |

**关键发现**：这两类**不是同一批行，不能互相替代**。存在 1 张 C 单数量为正、3,457 行非 C 单数量为负。若只按其中一个条件清洗，会漏掉另一批。

#### 发现 6｜单价异常 6,207 行

| 类别 | 行数 | 业务含义 |
|---|---|---|
| 单价 = 0 | 6,202 | 赠品、样品、内部调拨、损坏登记 |
| 单价 < 0 | 5 | 坏账调整（`Adjust bad debt`） |
| **合计** | **6,207** | |

#### 发现 7｜四个清洗条件的行数不能相加（方法论要点）

| 条件 | 独立计数 |
|---|---|
| ① 退货单（发票号 C 开头） | 19,494 |
| ② 数量 ≤ 0 | 22,950 |
| ③ 客户编号为空 | 243,007 |
| ④ 单价 ≤ 0 | 6,207 |
| **简单相加** | **291,658** |
| **任意一条命中（并集，去重后）** | **261,822** |
| **差值（重叠部分）** | **29,836** |

差值 29,836 说明约有 3 万行同时命中多个条件（例如一张退货单可能既以 C 开头、数量又为负、又缺客户编号）。

> **所以"脏数据总量"不能靠各条件计数相加得出** —— 相加会把同一行数两遍甚至三遍。正确做法是把所有条件用 `AND/OR` 组合写进同一个 `WHERE`，由数据库统一去重。

### 3.4 及时性

#### 发现 8｜末月数据不完整，直接算环比会得到假信号

| 月份 | 覆盖区间 | 覆盖天数 |
|---|---|---|
| 2010-12 | 12-01 ~ 12-23 | 20 天（12-24 起无数据＝圣诞停业，2011-01-04 恢复营业） |
| **2011-12** | **12-01 ~ 12-09** | **8 天（数据集截止）** |

**假信号演示**：

| 算法 | 结果 | 判定 |
|---|---|---|
| 直接环比：2011-12 vs 2011-11 | **−55.27%** | ❌ 假信号（8 天 vs 30 天，天数不可比） |
| 同口径：两年 12 月 1–9 日 | **+66.49%**（310,656.37 → 517,208.44） | ✅ 真实同比增长 |

剔除 2011-12-09 的异常大单（184,347.66）后，同口径增长为 **+22.17%**（更稳健的估计）。

对照组（天数相同的可比月）：2010-11 vs 2011-11 = 1,166,460.02 → 1,156,205.61，**−0.88%**。

> **这个案例的价值**：同一份数据，不懂口径会把"同比 +66%"讲成"环比暴跌 55%"，结论完全相反。

**处理动作**：末月（2011-12）标记为不可比；涉及该月的环比 / 同比统一改用同期口径；月度趋势分析一律先校验**每月覆盖天数与数据完整性**，再做对比。

## 四、验收结论

### 4.1 逐级剔除核对表（按清洗执行顺序累计）

| 步骤 | 剩余行数 | 本步剔除 |
|---|---|---|
| 起始（合并后 `retail_raw`） | 1,067,371 | — |
| ① 剔退货单（发票号 C 开头） | 1,047,877 | 19,494 |
| ② 再剔数量 ≤ 0 | 1,044,420 | 3,457 |
| ③ 再剔客户编号为空 | 805,620 | 238,800 |
| ④ 再剔单价 ≤ 0 | 805,549 | 71 |
| ⑤ 完全去重 | **779,425** | 26,124 |
| **合计剔除** | — | **287,946** |

**交叉校验**：287,946 ＝ 四条件并集 261,822 ＋ 去重 26,124 ✅
（两条独立路径得到同一结果，说明清洗链路闭合）

**累加口径与独立口径的差异说明**（这是必须能讲清的一点）：

| 条件 | 独立计数（3.3 节） | 累加口径（本节） | 差额 | 差额原因 |
|---|---|---|---|---|
| ② 数量 ≤ 0 | 22,950 | 3,457 | 19,493 | 已在步骤 ① 被剔除 |
| ③ 客户编号为空 | 243,007 | 238,800 | 4,207 | 已被步骤 ①② 剔除 |
| ④ 单价 ≤ 0 | 6,207 | 71 | 6,136 | 已被步骤 ①②③ 剔除 |

> 两组数字**对不上是正常的**：独立口径是"每个条件单独数一遍"（同一行会被数多次），累加口径是"前一步剔掉的不会再被后一步统计"。**能说清差异来源，才是真的做过对账。**

> ⚠️ 若漏掉第 ⑤ 步去重，结果会停在 805,549 —— 这一步正是 3.1 节"源文件时间重叠"的代价。

### 4.2 验收通过的基准值（后续所有分析的对账锚点）

| 校验项 | 基准值 |
|---|---|
| 合并后原始行数 | 1,067,371 |
| 原始表完全去重后行数 | 1,033,036 |
| **分析底表行数** | **779,425** |
| **分析底表总金额** | **17,374,804.27** |
| 唯一发票数 | 36,969 |
| 唯一商品数 | 4,631（默认排序规则口径） |
| 唯一客户数 | 5,878 |
| 时间下限 / 上限 | 2009-12-01 07:45:00 / 2011-12-09 12:50:00 |

**对账机制**：后续每一步分析（分组、聚合、分层、报表）均以上述数字为锚点。任何一步的结果无法与上一步闭合，即判定该步引入错误，必须回退定位，不进入下一步。

### 4.3 金额口径阶梯（改一个条件，数变多少）

| 口径 | 金额 | 与最终口径的差异 |
|---|---|---|
| ① 全量汇总（不去重、不清洗） | 19,287,250.57 | +1,912,446.30（+11.01%） |
| ② 剔除负数量后 | 20,972,594.57 | +3,597,790.30（+20.71%） |
| ③ 再去重后 | 20,476,260.45 | +3,101,456.18（+17.85%） |
| ④ **清洗后（本报告采用）** | **17,374,804.27** | 基准 |

**一个自查发现**：③ 与 ④ 的差额 **3,101,456.18**，与 3.2 节"散客金额"完全相等。
—— ③ 是"剔负 + 去重但未剔散客"的口径，因此它比最终口径多出的部分，正好就是散客的金额。**两个独立计算路径得到同一个数，构成一次有效交叉验证。**

## 五、实施过程记录（过程中遇到的两个问题）

本节记录两个只有真正动手才会遇到的问题，以及由此固定下来的两条自查动作。

### 问题 1｜日期列被识别为 TIME 型，106 万行的日期全部变成导入当天

| 环节 | 内容 |
|---|---|
| **现象** | 原始文件第一行是 `2009-12-01 07:45:00`，导入后表里是 `2026-09-20 07:45:00` —— **日期变成了执行导入那天，时间部分倒是对的** |
| **原因** | 首次导入时该列被建成了 `TIME` 类型（只存时间、不存日期）。之后执行 `ALTER TABLE ... CHANGE COLUMN ... DATETIME` 时，MySQL 用「当前日期」补齐了日期部分 |
| **危险之处** | **不报错、不丢行、总金额完全正常** —— 只有日期悄悄坏了。若按常规只检查行数与金额，这个错误会被完全放过 |
| **怎么发现的** | 做月度分析时发现所有记录落在同一个月，反查 `MIN/MAX(开票时间)` 才暴露 |
| **处理** | 重新导入并显式指定日期类型；脚本中不再做任何 `ALTER` |

**由此固定下来的自查动作**：导入后第一件事不是查行数，而是查时间范围与跨度。

```sql
SELECT MIN(invoice_date), MAX(invoice_date),
       DATEDIFF(MAX(invoice_date), MIN(invoice_date)) AS 跨天数
FROM <表名>;
-- 正常：2009-12-01 ~ 2010-12-09，跨 373 天
-- 损坏：最早与最晚落在同一天
```

> 这也是本报告第二节把「及时性」列为独立检查维度的原因 —— 它检查的是**时间字段本身是否可信**，而不只是业务数据对不对。

### 问题 2｜清洗脚本重复执行，导致数据翻倍

| 环节 | 内容 |
|---|---|
| **现象** | 清洗后行数变成 1,558,850、总金额 34,749,608.54 —— 恰好是正确值的两倍 |
| **原因** | 脚本由「建表」和「插入」两段组成，重复执行时只重跑了插入段，没有重建表 |
| **处理** | 改写为 `DROP TABLE IF EXISTS` → `CREATE TABLE` → `INSERT ... SELECT` 的完整段落，**必须整段一起执行**；执行后立即查行数与金额自查 |

> 这两条构成了 4.2 节「对账锚点」的来源 —— **对账机制不是设计出来的，是踩出来的。**

## 七、局限与下一步

本报告只完成"数据能不能用"的验收，未回答"业务上该如何判断"。下一步计划：

1. **月度趋势**：先校验每月数据完整性，再做同口径比较（末月不做环比）
2. **客户分层**：先确认"最近一次消费"的观察截止日口径，再分层
3. **复购率**：同时提供整体口径与窗口口径，并在报表上标注分母定义

> 口径差异说明：本数据集下，复购率按**整体口径**为 72.39%（4,255 / 5,878），按**30 天窗口口径**为 23.31%（1,370 / 5,878）。两个都"对"，取决于业务想问"整体粘性"还是"短期行为"。
> **指标是有立场的 —— 报表必须写明分母，否则同一个数字会被读出两种结论。**

## 附：可复现性说明

本报告全部数字均在本机 MySQL 8.0 上实跑得出。清洗脚本采用 `DROP TABLE IF EXISTS` → `CREATE TABLE` → `INSERT ... SELECT` 三段式，可整段重复执行。

核心验收语句：

```sql
SELECT COUNT(*) AS 行数, ROUND(SUM(amount), 2) AS 总金额
FROM retail_clean;
-- 779,425 ｜ 17,374,804.27
```

清洗条件（4 个条件 + 完全去重）：

```sql
SELECT DISTINCT
  invoice, TRIM(stock_code), TRIM(description), quantity,
  invoice_date, unit_price, customer_id, TRIM(country),
  quantity * unit_price AS amount
FROM retail_raw
WHERE invoice NOT LIKE 'C%'      -- ① 剔退货冲销单
  AND quantity > 0               -- ② 剔负数量
  AND customer_id IS NOT NULL     -- ③ 剔散客
  AND unit_price > 0;             -- ④ 剔零价与负价
```

**工具链**：Navicat（查询与导入）· MySQL 8.0（清洗与校验）· Excel（辅助核对）
