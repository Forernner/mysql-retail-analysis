# 电商交易数据分析（MySQL + Power BI）

对 UCI Online Retail II 公开数据集（**106.7 万行**）完成的端到端分析：
从数据清洗、建模，到交互式可视化看板。

**这是同一个项目的两个阶段** —— 上游用 MySQL 把数据洗干净并做探索分析，
下游用 Power BI 建星型模型、写 DAX 度量值、出交互看板。

## 阶段一 · MySQL：清洗与探索

### 清洗逻辑

原始数据有四个问题，外加一个**很隐蔽的坑**：

| # | 问题 | 处理方式 |
|---|---|---|
| 1 | 取消订单（`InvoiceNo` 以 `C` 开头） | 过滤 |
| 2 | 数量 ≤ 0（退货与库存调整） | 过滤 |
| 3 | 单价 ≤ 0 | 过滤 |
| 4 | 客户编号缺失（约 23%） | 过滤 |
| 5 | **两个源文件的时间区间重叠 9 天** | `DISTINCT` 去重 |

清洗链路：**4 个条件过滤 + `DISTINCT` 去重 + 三列 `TRIM`**（部分文本列存在尾随空格）。

### 第 5 个坑最隐蔽

两个源文件在 **2010-12-01 ~ 09 这 9 天完全重叠**，产生 **34,335 行一模一样的记录**。

**不去重的话，2010 年 12 月的流水会虚高 55%** —— 而当月总金额看起来**完全正常**，
只看汇总数字根本发现不了。

### 用到的 SQL 技术

- 多表合并（`UNION ALL`，保留重复行以便事后核查）
- 条件清洗 + 去重（`DISTINCT`、`TRIM`）
- 派生列（`amount = quantity × unit_price`）
- 分组聚合（`GROUP BY` + `HAVING`）
- **窗口函数** —— `ROW_NUMBER` 做分组编号取首单、`SUM() OVER` 做累计占比（帕累托）
- **CTE**（`WITH`）把多步查询拆开写
- 标量子查询（算「占全表」的百分比）

## 阶段二 · Power BI：建模与可视化

### 星型模型

一张事实表 + 四张维度表，**四条一对多、单向关系**（筛选方向从维度表流向事实表）。

| 表 | 类型 | 行数 |
|---|---|---|
| `retail_clean` | 事实表 | 779,425 |
| 日期表 | 维度表 | 739 |
| 客户表 | 维度表 | 5,878 |
| 商品表 | 维度表 | 4,631 |
| 国家表 | 维度表 | 41 |

### DAX 度量值

共 10 个，其中几个关键的：

```dax
GMV = SUM ( retail_clean[amount] )

客单价 = DIVIDE ( [GMV], [订单数] )

复购客户数 =
COUNTROWS (
    FILTER (
        VALUES ( retail_clean[customer_id] ),
        CALCULATE ( DISTINCTCOUNT ( retail_clean[invoice] ) ) >= 2
    )
)

上月GMV = CALCULATE ( [GMV], DATEADD ( '日期表'[Date], -1, MONTH ) )
月环比 = DIVIDE ( [GMV] - [上月GMV], [上月GMV] )
```

### 看板内容

四个指标卡（GMV / 订单数 / 客户数 / 客单价）给出规模底盘，
月度趋势折线看节奏，国家分布条形看结构，左侧切片器（年 / 国家 / 商品）可联动筛选。

图表标题直接写成结论 —— **标题是唯一每个人都会读的文字，不该让人自己看图猜结论**。

## 结论

**1. 规模** —— 两年累计营收 **1,737.5 万元**，**36,969** 笔订单，**5,878** 位客户，客单价 **469.98 元**

**2. 节奏** —— **9–11 月连续走高，11 月为全年峰值**（2010-11 = 116.6 万，2011-11 = 115.6 万，
同比仅 **−0.88%**）。**两年是完全一样的模式**，典型的圣诞礼品季节性。

**3. 结构** —— 英国贡献 **82.82%**，第二名爱尔兰只有 **3.55%**，市场高度集中。

**4. 一个口径发现** —— 月度环比表上 2011-12 显示 **−55.27%**，看起来像暴跌。
**它是假信号**：

| 月份 | 有交易的天数 | GMV |
|---|---|---|
| 2010-11 | 26 | 1,166,460.02 |
| 2011-11 | 26 | 1,156,205.61 |
| 2010-12 | **20** | 570,422.73 |
| 2011-12 | **8** | 517,208.44 |

11 月两年都是 26 个交易日 → 可比 → 同比 −0.88% 是**真实信号**。
12 月一个是 20 天、一个是 8 天 → 环比和同比**都不成立**。

同口径重算（只取两年都完整的 12 月 1–9 日）：`310,656.37 → 517,208.44` = **+66.49%**

> **同一个 12 月：直接算是「暴跌 55%」，同口径算是「增长 66%」，差了 120 个百分点。**
>
> 这个坑最麻烦的地方是：**总金额看上去完全正常**。不逐日核对天数，从报表上看不出任何异常。

## 关于可信度

**`verify/` 目录里放着每个查询的原始输出。**

所有数字都是从数据库跑出来的，不是估算、也不是从别处转述。
如需复核，按 `sql/` → `verify/` 的顺序执行即可。

另外，**同一套核心指标在 MySQL 与 Power BI 两侧做过双轨核对，15 个指标完全一致** ——
这也是两个阶段之间没有断层的证据。

## 说明

DAX 度量值的写法借助 AI 起草，但**每一个都拿 MySQL 侧的基准数字逐条校验过**
（例如 GMV 必须等于 `17,374,804.27`，对不上就回头查）。

至于口径怎么定义、该用哪一个 —— 这部分由分析者决定，不交给工具。
