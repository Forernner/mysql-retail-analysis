# verify/ · 验证记录

> 本目录覆盖项目的 **MySQL 阶段**（清洗与探索分析）。Power BI 阶段的文件见 `../powerbi/`。

这个目录是项目的**证据库**。

## 里面是什么

每一个 `NN_*.sql` 都是**实际执行过**的查询，配套的 `NN_out.txt` 是它的**原始运行输出**
（从 MySQL 命令行直接导出，未做任何修改）。

```
01_inspect.sql    →  01_out.txt      # 查看原始表结构
05_nulls.sql      →  05_out.txt      # 统计空值分布
06_load.sql       →  06_out.txt      # 导入数据
07_build.sql      →  07_out.txt      # 建清洗表
20_recon.sql      →  20_out.txt      # 对账
21_december.sql   →  21_out.txt      # 12 月天数核查
100_groupby_why.sql → 100_out.txt    # 验证聚合行为
140_nonproduct.sql → 140_out.txt     # 识别非商品条目
```

**统计**：24 个 SQL 脚本，其中 **22 个配有独立的输出记录文件**。

`_process/` 子目录放的是过程记录 —— 索引性能测试脚本、执行状态快照、`EXPLAIN` 结果等，
属于过程中产生的工作文件，保留下来是为了让过程可追溯。

## 为什么要放这个目录

**数据项目最容易出的问题是"数字是怎么来的"说不清。**

把所有查询和它们的原始输出放在一起，任何人都可以：

1. 打开 `NN_*.sql` 看**查询逻辑**
2. 打开 `NN_out.txt` 看**它当时跑出来什么**
3. 自己复算一遍，验证是否一致

这比任何"我做了完整的数据清洗"的表述都更可信。

## 几个值得看的

| 文件 | 看什么 |
|---|---|
| `20_recon.sql` / `20_out.txt` | **对账**：清洗链路的闭合验证 |
| `21_december.sql` / `21_out.txt` | **12 月天数核查**：发现"假信号"的那一步 |
| `100_groupby_why.sql` / `100_out.txt` | 验证 `GROUP BY` 的聚合行为 |
| `140_nonproduct.sql` / `140_out.txt` | 识别商品榜里的非商品条目（Manual / POSTAGE） |

> ⚠️ 这些输出里可能包含我探索过程中的中间结果和试错记录 —— **它们没有被清理美化过**，
> 因为它们的作用是"证明过程真实"，不是"展示漂亮结果"。

## 两个说明

**① 输出文件开头这一行是 MySQL 客户端的标准提示，与查询内容无关：**

```
mysql: [Warning] Using a password on the command line interface can be insecure.
```

用 `mysql -p<密码>` 方式连接时必然会打印它（提醒明文传密码不安全）。
**它里面不包含任何密码。**

**② `_process/` 里的 Python 脚本中，数据库密码已替换为占位符：**

```
"-p<YOUR_PASSWORD>"
```

复现时请填自己的密码。把密码硬编码进脚本、再提交到公开仓库，是不该犯的错误。
