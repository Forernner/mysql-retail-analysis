### Q1 · 表结构体检 ｜★｜5 分钟 ｜3 分

**先跑这两句，看清你手上两张表长什么样 + 时间列对不对**

```sql
SHOW FULL COLUMNS FROM online_retail_year_2009_2010;
SHOW FULL COLUMNS FROM online_retail_year_2010_2011;

-- ★ 时间列体检（比行数更重要，这一步能提前抓住"日期坏了"）
SELECT MIN(invoice_date) AS 最早, MAX(invoice_date) AS 最晚,
       DATEDIFF(MAX(invoice_date), MIN(invoice_date)) AS 跨天数
FROM online_retail_year_2009_2010;
```

**要回答的三个问题**

| 问题 | 参考回答 |
|---|---|
| **你导入后只查了行数，够不够？该再查什么？** | **不够。必须再查 `MIN/MAX(日期)` 和天数跨度。** 我这张表最初 `InvoiceDate` 被自动识别成 **`TIME` 类型**（只存时间），后来 `ALTER ... DATETIME` 转类型时，**MySQL 用「当前日期」补齐了日期部分** —— 106 万行的日期全变成执行 ALTER 那天，时间部分却是对的。行数、金额全都正常，**只有日期悄悄坏了**。正常应跨 **373 天**，损坏时跨 **0 天**（全是同一天） |
| `Price` 用了什么类型？ | 现在已经是 **`DECIMAL(10,4)`**（脚本已改过）。记住结论：**金额不能用 `FLOAT`/`DOUBLE`** —— 原数据里就有 `2.5499999999999998` 这种浮点尾数；`DECIMAL(10,4)` 能装下 999,999.9999，对本数据够用 |
| 能不能给这两张表加 `PRIMARY KEY`？ | **不能加 `(invoice, stock_code)` 主键** —— 同一张发票、同一个商品可以有多条明细行（不同价格 / 不同批次），加主键会直接报 `Duplicate entry` |

**参考答案 SQL（只需要自查，不用改结构）**

```sql
-- 1) 列名与类型
SHOW FULL COLUMNS FROM online_retail_year_2009_2010;

-- 2) 时间列体检：跨天数应约等于 373
SELECT DATEDIFF(MAX(invoice_date), MIN(invoice_date)) AS 跨天数
FROM online_retail_year_2009_2010;

-- 3) 排序规则
SELECT table_name, table_collation FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND table_name IN ('online_retail_year_2009_2010', 'online_retail_year_2010_2011');
```

**判分（3 分，每条 1 分）**

| 要点 | 说明 |
|---|---|
| **说出"导入后要查时间范围 / 天数跨度"** | 这是本题的核心，也是最值钱的一条 —— `ALTER` 把 `TIME` 补成当天日期这种事，只查行数永远发现不了 |
| 知道 `description` 必须允许 NULL | 原数据有 **4,382 行**商品名为空，设成 NOT NULL 会导不进来 |
| 知道不能加 `(invoice, stock_code)` 主键 | 面试官问"你建表踩过什么坑"，这就是标准答案 |

**顺带记住两个列类型结论**

- `quantity` / `unit_price` **都不能用 `UNSIGNED`**（两列都有负数，见 Q5）
- `stock_code` **必须是 `VARCHAR` 不能是 `INT`**（混有 `POST` / `DOTS` / `M` / `B` / `47503J ` 这类非纯数字码）

### Q2 · 两表行数校验 + 发现重复行 ｜★★（仅 ①②）｜6 分钟 ｜3 分

> **【2026-09-21 难度修正】这题原来是 ★★｜8 分钟，但它其实是三个难度完全不同的问，已拆开：**
>
> | | 内容 | 什么时候做 |
> |---|---|---|
> | **①②** | 报两张表行数 / 合并行数 / 去重后行数 | **Day 2 必做**（会用 `UNION ALL` 和 `SELECT DISTINCT *` 就够） |
> | **③** | 差额从哪来 + 定位到月份 | **挪到 Day 4**。它要「多列 GROUP BY + HAVING + 时间函数 + 两级分组」，真实难度 ★★★★，放 Day 2 会卡住你 |
>
> **Day 2 你只需要看懂 ③ 的结论表**（下面已经给了），不需要自己写那段 SQL。

**第一问：两张表各多少行？**

```sql
SELECT 'online_retail_year_2009_2010' AS 表名, COUNT(*) AS 行数 FROM online_retail_year_2009_2010
UNION ALL
SELECT 'online_retail_year_2010_2011',          COUNT(*)          FROM online_retail_year_2010_2011;
```

**标准答案**

| 表 | 行数 |
|---|---|
| `online_retail_year_2009_2010` | **525,461** |
| `online_retail_year_2010_2011` | **541,910** |
| **合并（UNION ALL）= retail_raw** | **1,067,371** |

**第二问（本卷的第一个真发现）：这 1,067,371 行里有重复行**

```sql
SELECT COUNT(*) AS 合并行数 FROM retail_raw;                              -- 1,067,371
SELECT COUNT(*) AS 完全去重后行数 FROM (SELECT DISTINCT * FROM retail_raw) x;  -- 1,033,036
--                            ↑ 别名必须有：少了报 1248
--                              若报 1064 near 'FROM retail_raw)' → DISTINCT 后的 * 丢了（复制粘贴常见）
```

> **1,067,371 − 1,033,036 = 34,335 行是完全重复的（占 3.22%）。**

**第三问（③ 选做 · 挪到 Day 4）重复行从哪来？两个来源**

> Day 2 **不用写这段 SQL**，看懂下面的结论表就行。Day 4 学完窗口函数 / CTE 后回来补。
> 现在想看懂的话 —— **先读「逐行拆解」，它比时间函数重要得多。**

```sql
-- 来源①：重复行集中在哪个月
SELECT DATE_FORMAT(invoice_date, '%Y-%m') AS 月份, SUM(c - 1) AS 被去掉的重复行数
FROM (
  SELECT invoice_date, COUNT(*) AS c
  FROM retail_raw
  GROUP BY invoice, stock_code, description, quantity, invoice_date,
           unit_price, customer_id, country
  HAVING COUNT(*) > 1
) t
GROUP BY 月份 ORDER BY 被去掉的重复行数 DESC;
```

**逐行拆解：为什么"分了组还要再分组"**（2026-09-21 在你本机 MySQL 8.0 实跑验证）

| 步骤 | SQL 片段 | 它在干什么 | 实际结果 |
|---|---|---|---|
| ① | `FROM retail_raw` | 全表出发 | 1,067,371 行 |
| ② | `GROUP BY invoice, stock_code, description, quantity, invoice_date, unit_price, customer_id, country` + `COUNT(*) AS c` | **按"全部 8 列"分组**：8 个值一模一样的行算一组，数出每组几行 = `c` | 得到"每一行组合出现过几次" |
| ③ | `HAVING COUNT(*) > 1` | **只留出现 2 次及以上的组**（`WHERE` 筛不了聚合结果，所以必须用 `HAVING`） | **32,907 组** |
| ④ | 外层 `GROUP BY 月份` + `SUM(c - 1)` | 把剩下的组按月份归类，每组贡献 `c - 1` 行 | 2010-12 最多 **23,023**；**合计 34,335** |

**为什么必须按「全部 8 列」分组 —— 只按 customer_id 会错 31 倍**（2026-09-21 实跑对比）

`GROUP BY` 的列，就是你对「**什么算同一件事**」的定义。列选少了，等于把不同的事强行算成同一件。

| 分组方式 | 算出的"多出来的行数" | 对不对 |
|---|---|---|
| **按全部 8 列**（整行） | **34,335** | ✅ 与 `1,067,371 − 1,033,036` 完全一致 |
| 只按 `customer_id` | **1,061,428** | ❌ **虚高 31 倍** |
| 只按 `invoice` | 1,013,743 | ❌ 虚高 30 倍 |

**为什么只按 customer_id 会离谱**：一个客户会下很多单、买很多商品。按客户分组，
等于在说"这个客户的所有消费记录都是同一笔" —— **那不是找重复，那是数复购。**

**真实反例（客户 12346 的三行）**：

| 发票号 | 发票时间 | 数量 | 商品码 |
|---|---|---|---|
| 491725 | 2009-12-14 08:34 | 10 | TEST001 |
| 491742 | 2009-12-14 11:00 | 5 | TEST001 |
| 491744 | 2009-12-14 11:02 | 5 | TEST001 |

同客户、同商品，但**发票号、时间、数量都不同** → 3 笔独立交易、**0 行重复**。
只按 customer_id 分组会把它们并成 1 组、报出 2 行"重复" —— 纯属虚构。

**★ 一句话自检（记住就不会错）**

> 你用来分组的列，必须和你**去重时用的列**一致。
> 去重用的是 `SELECT DISTINCT *`，`*` 代表**全部列** → 所以分组也必须用全部列。
> **验算**：`SUM(c - 1)` 必须等于 `原始行数 − 去重后行数`。对不上，就是分组列选错了。

**两个要理解的点（不是记住，是理解）**

1. **为什么要两级分组**：内层回答的是"**哪些行重复了、重复几次**"；外层回答的是"**这些重复分布在哪些月份**"。
   一次 `GROUP BY` 只能回答一个问题，所以必须套两层。**这就是"派生表 + AS t"最典型的用法。**
2. **为什么是 `SUM(c - 1)`**：一组出现 `c` 次，去重后只留 1 行，所以**多出来的是 `c - 1` 行**。
   全部加起来 = **34,335**，正好等于 `1,067,371 − 1,033,036` —— 两条路算出来的数能对上，这才叫验证过。

**③ 里唯一的时间函数：`DATE_FORMAT`**

| 想要的 | 写法 | 结果 |
|---|---|---|
| 取「年-月」文本 | `DATE_FORMAT(invoice_date, '%Y-%m')` | `'2010-12'` ← **是字符串，不是日期** |
| 只去掉时分秒 | `DATE(invoice_date)` | `'2010-12-05'` |
| 只取年 / 只取月（数字） | `YEAR(...)` / `MONTH(...)` | `2010` / `12` |

- `%Y` = 4 位年，`%m` = 2 位月（**小写 `%m` 是月，`%i` 才是分钟**，别写混）。
- **为什么能拿它分组**：`'2010-12'` 这种写法**按文本排序恰好等于按时间排序**（`'2010-12' < '2011-01'`），
  所以按月分组的顺序天然就是对的。
- 类比 Excel：`DATE_FORMAT(d,'%Y-%m')` ≈ `TEXT(A1,"yyyy-mm")`。
- 📌 **完整的时间函数速查在本文档末尾「附录 A」**，Day 3–4 会反复用。


| 来源 | 行数 | 说明 |
|---|---|---|
| **跨表重复** | **22,202** | 两张表的时间范围在 **2010-12-01 ~ 12-09 这 9 天重叠**，同一行记录在两张表里各存了一份 |
| **表内重复** | **12,133** | `2009-2010` 表自身 6,865 行 + `2010-2011` 表自身 5,268 行，散布在 25 个月里 |
| 合计 | **34,335** | 重复行最多的月份 = **2010-12（23,023 行）** |

**⚠️ 这一步为什么是全卷最重要的地方**

如果不去重，**2010 年 12 月的流水会被算了将近两遍**（不去重的错数：884,591.89；正确值：570,422.73，**高了 55.08%**）。后面所有按月、按国家、按商品的金额**全部会错**，而且错得很隐蔽 —— 因为"总金额"看上去很正常。

**判分（3 分，只看 ①②）**：两表行数对 + 合并行数对 1 分；发现重复并说出 **34,335** 这个数 1 分；
**说出"因为两张表时间范围重叠"并定位到 2010-12 得 1 分**。

> ⚠️ **注意**：这 3 分**都不要求你写出 ③ 那段 SQL** —— "原因"和"月份"在下面的结论表里就有。
> ③ 是**看懂就算赚到**的加分项，Day 4 再动手写。

> **💼 这就是你作品集/面试里最值钱的一句话**

### Q3 · 时间范围校验 + 重叠期 ｜★★｜6 分钟 ｜3 分

```sql
SELECT '2009_2010' AS 表, MIN(invoice_date) AS 最早, MAX(invoice_date) AS 最晚
FROM online_retail_year_2009_2010
UNION ALL
SELECT '2010_2011', MIN(invoice_date), MAX(invoice_date)
FROM online_retail_year_2010_2011;

SELECT MIN(invoice_date) AS 全期最早, MAX(invoice_date) AS 全期最晚 FROM retail_raw;
```

**标准答案**

| 表 | 最早 | 最晚 |
|---|---|---|
| `online_retail_year_2009_2010` | 2009-12-01 07:45:00 | **2010-12-09 20:01:00** |
| `online_retail_year_2010_2011` | **2010-12-01 08:26:00** | 2011-12-09 12:50:00 |
| 合并（retail_raw） | 2009-12-01 07:45:00 | 2011-12-09 12:50:00 |

→ **两张表在 2010-12-01 ~ 2010-12-09 重叠了 9 天**，这正是 Q2 里 22,202 行跨表重复的来源。

**🔴 全卷最重要的一个坑（记牢，Q19/Q21 会再用到）**

**两个 12 月都不能当完整月用，但"残"的原因不一样：**

| 月份 | 实际覆盖 | 有数据天数 | 为什么 |
|---|---|---|---|
| 2010-12 | 12-01 ~ **12-23** | 20 天 | 12-24 ~ 12-31 **一笔数据都没有** → 圣诞停业（下一笔交易要到 2011-01-04） |
| 2011-12 | 12-01 ~ **12-09** | 8 天 | **数据集到此截止**（2011-12-09 12:50 是最后一个时点） |

所以：

> **2011 年 12 月流水 517,208.44，环比 11 月掉 55.27% —— 责任在"只有 8 天"。**
> **2010 年 12 月流水 570,422.73，环比 11 月掉 51.10% —— 责任在"只有 20 天"。**

两个月都是**"天数不一样"造成的假信号**，不是业务崩盘。**在作品集和面试里拿这个环比说事，会当场翻车。** 正确做法：

1. 报告里写明"这两个月天数不完整，不参与环比"；
2. **同口径对比**（这是能说出口的结论）—— 只取两年都有数据的 **12 月 1–9 日**：

   | | 12-01 ~ 12-09 |
   |---|---|
   | 2010 | 310,656.37 |
   | 2011 | **517,208.44** |
   | 同比 | **+66.49%** ⬆️ |
   | 剔除 2011-12-09 那笔异常大单（单日 184,347.66 / 41 单）后 | **+22.17%** ⬆️ |

   → **同口径看是"增长"，不是"暴跌"。** 换句话说：**不查口径，你会把增长讲成崩盘。**
3. 真要比月度，就比**天数相同的月**：2010-11（26 天）vs 2011-11（26 天）= 1,166,460.02 → 1,156,205.61 = **−0.88%**。

**判分（3 分）**：两表时间范围对 1 分；识别出重叠 9 天 1 分；**主动指出两个 12 月天数不完整、并给出同口径替代口径 1 分**。

### Q4 · 五个体检数字 ｜★★｜6 分钟 ｜4 分

```sql
SELECT
  COUNT(*)                    AS rows_total,
  COUNT(DISTINCT invoice)     AS invoices,
  COUNT(DISTINCT stock_code)  AS items,
  COUNT(DISTINCT customer_id) AS customers,
  COUNT(DISTINCT country)     AS countries
FROM retail_raw;
```

**标准答案**

| 指标 | 原始（retail_raw） | 清洗后（retail_clean） |
|---|---|---|
| 总行数 | **1,067,371** | **779,425** |
| 唯一发票数 | **53,628** | 36,969 |
| 唯一商品编码数 | **5,132** ⚠️ | 4,631 |
| 唯一客户 ID 数 | **5,942** | 5,878 |
| 唯一国家数 | **43** | **41** |

**判分**：5 个原始数字全对 4 分；错 1 个扣 1 分。
**注意商品数**：报 5,132 才对（见下面第 2 条）；如果你报的是 5,305 或 5,304，不扣分但要能说清为什么 —— 那是排序规则的差异。

**三个必须能解释的点**

1. **`COUNT(DISTINCT customer_id)` 自动忽略 NULL**，所以得到的是 5,942 个"有 ID 的客户"，不含 24.3 万行散客。写成 `COUNT(customer_id)` 会得到一百万级别的错数。
2. **唯一商品数到底是几？—— 取决于排序规则，同一列能数出三个答案（本题的分水岭）**

```sql
SELECT COUNT(DISTINCT stock_code)                          AS 默认口径,        -- 5,132
       COUNT(DISTINCT stock_code COLLATE utf8mb4_bin)      AS 区分大小写,      -- 5,304
       COUNT(DISTINCT stock_code COLLATE utf8mb4_0900_bin) AS 全都区分         -- 5,305
FROM retail_raw;
```

| 写法 | 结果 | 为什么 |
|---|---|---|
| 默认 `utf8mb4_0900_ai_ci` | **5,132** | **忽略大小写** → `15056BL` 和 `15056bl` 算一个（这类变体有 **172 组**） |
| `COLLATE utf8mb4_bin` | **5,304** | 区分大小写，但它是 **PAD SPACE** → `47503J ` 和 `47503J` 又算一个 |
| `COLLATE utf8mb4_0900_bin` | **5,305** | 大小写、尾空格都区分 —— 和 Python / CSV 侧一致 |

   **编码 `47503J ` 尾随一个空格**（出现 80 次），无空格的 `47503J` 只出现 1 次 —— 这就是清洗必须 `TRIM(stock_code)` 的原因。
   **报告里必须写明用的是哪种口径**，否则同一个"商品数"你说 5,132、面试官说 5,305，两边都觉得对方错了。
3. **清洗后为什么少了 2 个国家？** 被剔掉的两个国家是 **Bermuda（百慕大）** 和 **Hong Kong（中国香港）** —— 它们只出现在无客户 ID 的散客订单里，剔散客时一起走了。**这是清洗的副作用，要在报告里交代。**

### Q6 · 粒度一致性体检 ｜★★★｜10 分钟 ｜4 分

```sql
-- 一张发票是否只对应一个客户、一个国家？
SELECT invoice,
       COUNT(DISTINCT customer_id) AS c_cnt,
       COUNT(DISTINCT country)     AS n_cnt
FROM retail_raw
GROUP BY invoice
HAVING c_cnt > 1 OR n_cnt > 1;
```

**标准答案：返回 0 行** —— 即「一张发票 = 一个客户 + 一个国家」在本数据集中成立。

**但真正的发现在这里**：

```sql
SELECT COUNT(*) FROM retail_raw WHERE invoice LIKE 'A%';
```

→ **6 行**。这些是 `Adjust bad debt`（坏账调整），**UnitPrice 全是巨额负数**（-53,594.36 等），不是商品交易。它们是"财务调整单"，混在商品流水里。

**判分**：查出 0 反例得 2 分；发现 A 开头这 6 行得 4 分（这题的分主要在这）。

**坑**：如果你只回答"没有反例"就结束了，你会漏掉 `A` 开头这一类。**清洗时它们会被 `unit_price > 0` 顺手剔掉 —— 但你必须知道剔的是什么。**

### Q9 · 缺失诊断 ｜★｜5 分钟 ｜3 分

```sql
SELECT
  SUM(CASE WHEN customer_id IS NULL THEN 1 ELSE 0 END) AS null_rows,
  ROUND(SUM(CASE WHEN customer_id IS NULL THEN 1 ELSE 0 END)
        * 100.0 / COUNT(*), 2)                         AS pct
```

**标准答案：243,007 行，占 22.77%**

**判分**：行数对 2 分；百分比对 3 分。

**坑**：`IS NULL` 和 `= ''` 要**都写**（这里因为合并时已经用 `NULLIF(NULLIF(customer_id,''),0)` 统一过了，所以只有 NULL；但你得知道为什么要统一）。这也是为什么建表时 `customer_id` 存成 INT 比存成字符串更干净 —— 只有一种空值。

|---|---|
| C 开头（退货单）总行数 | **19,494** |
| └ 其中数量 < 0 | **19,493** |
| └ 其中数量 > 0 | **1** ⚠️ |
| └ 其中数量 = 0 | 0 |
| └ 其中客户 ID 为空 | 750 |
| **非 C 开头但数量 < 0** | **3,457** ⚠️ |
| 退货率（C 单 ÷ 总行数） | **1.83%** |

**🔴 这题是整卷的第二个关键洞察**

> **「按 C 开头剔」和「按负数剔」不是同一批行。**

- 有 **1 行** 是 C 单但数量为正 → 只按 C 剔会**误剔**一条正常交易
- 有 **3,457 行** 是非 C 单但数量为负 → 只按 C 剔会**漏剔** 3,457 条负流水

**结论：必须两个条件都写**（`invoice NOT LIKE 'C%' AND quantity > 0`）。这也是面试最爱的"你清洗时踩过什么坑"的标准答案。

**判分**：19,494 对 2 分；发现 3,457 这个数 5 分。
