### Q13 · 清洗落表（4 条件 + 去重）｜★★★★｜14 分钟 ｜6 分

**这是本卷唯一一道必须完全写对的题。**

> ## ⚠️ 动手前必读：这段是「DROP + CREATE + INSERT」三句一体的
>
> **必须整段一起跑。** 2026-09-21 真实事故：只跑到 `CREATE TABLE` 就停手 →
> **真表被删掉、新表是空的**，而**屏幕上不报任何错**，后面所有题的查询结果全是 0，极难自查。
>
> **跑完立刻自查**：
> ```sql
> SELECT COUNT(*) FROM retail_clean;   -- 必须是 779,425
> ```
>
> 🛡️ **更安全的练法（建议第一次这么做）**：把表名临时改成 `retail_clean_test` 先练一遍，
> 数字对上了，再把表名改回 `retail_clean` 正式落一次；练完
> `DROP TABLE retail_clean_test;` 收掉。
>
> 📌 这题本质上就是**你自己重做一遍 `SQL_00` 的第 2 段**（那儿已经有一份能跑的版本可对答案）。

**这题在面试里会怎么考 —— 考的从来不是建表语法**

| 形式 | 频率 | 面试官真正在看什么 |
|---|---|---|
| 给一个业务场景，问"你会建哪些表、哪些字段" | **高**（数据岗 / 数据产品岗） | 你知不知道要留哪些维度、什么粒度 |
| "金额这一列为什么用 `DECIMAL` 不用 `FLOAT`" | 中高 | 精度意识 |
| "这一列该用 `INT` 还是 `VARCHAR`" | 中 | 会不会结合业务取值判断（你的商品编码含 `POST`/`M`） |
| "为什么加索引 / 加在哪一列" | 中 | 查询模式（见《第00步》坑④） |
| 让你现场写完整的 `CREATE DATABASE` | **几乎不考** | — |
| 考字符集 / 排序规则细节 | 低（除非 DBA 岗） | — |

> **结论**：`CREATE DATABASE` 不用花时间背；`CREATE TABLE` 要会，但**分数在「字段类型 + 约束 + 为什么」上**。
> 而**这道 Q13 的 6 分几乎全在 4 个 `WHERE` 和 `DISTINCT` 上** —— 建表只是外壳。



```sql
DROP TABLE IF EXISTS retail_clean;

CREATE TABLE retail_clean (
  invoice      VARCHAR(20)   NOT NULL,
  stock_code   VARCHAR(20)   NOT NULL,
  description  VARCHAR(200)  NULL,
  quantity     INT           NOT NULL,
  invoice_date DATETIME      NOT NULL,
  unit_price   DECIMAL(10,4) NOT NULL,
  customer_id  INT           NOT NULL,
  country      VARCHAR(60)   NOT NULL,
  amount       DECIMAL(12,4) NOT NULL COMMENT '派生列 = quantity * unit_price',
  KEY ix_date (invoice_date),
  KEY ix_cust (customer_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO retail_clean
SELECT DISTINCT                    -- ★ 第 5 件事：完全去重
  invoice,
  TRIM(stock_code),
  TRIM(description),
  quantity,
  invoice_date,
  unit_price,
  customer_id,
  TRIM(country),
  quantity * unit_price
FROM retail_raw
WHERE invoice NOT LIKE 'C%'          -- ① 剔退货单：不是销售，是冲销
  AND quantity > 0                   -- ② 剔负数量：同上；顺带剔掉数量为 0 的行
  AND customer_id IS NOT NULL        -- ③ 剔散客：无 ID 无法做客户级留存/复购
  AND unit_price > 0;                -- ④ 剔零价与负价：赠品无金额意义，负价是坏账调整
```

**标准答案：清洗 + 去重后 779,425 行**

**判分（6 分）**

| 要点 | 分值 | 为什么 |
|---|---|---|
| 4 条 WHERE 一条不少 | 3 分 | 缺任何一条，后面所有分析口径都会歪 |
| **`SELECT DISTINCT` 去重** | 1 分 | 不去重 → 779,425 变成 805,549，2010-12 流水虚高 55% |
| `TRIM(description)` / `TRIM(stock_code)` | 1 分 | 商品名带**尾随空格**：清洗口径的 805,549 行里有 **163,286 行（20.3%）**（其中尾随 161,767 / 前导 2,019）；全表则是 **213,035 行**。商品编码有 1 个带尾空格（`47503J `，出现 80 次）。不去 → `GROUP BY` 把同一商品算成两个 |
| 派生 `amount` 列 + 先建表再 INSERT | 1 分 | `CREATE TABLE ... AS SELECT` 不继承索引/字符集，106 万行会很慢 |

**坑**

- **不要给这张表加 `(invoice, stock_code)` 主键** —— 同一发票同一商品可以有多行。
- `SELECT DISTINCT` 是对**全部输出列**去重（含 `TRIM` 后的列），所以它同时也顺手干掉了"只差一个尾随空格"的伪重复行。
- `TRIM(country)` 之后，清洗后的国家数从 43 变成 **41**（Bermuda、Hong Kong 只在散客订单里出现）。

### Q14 · 清洗决策（主观）｜★★★★｜15 分钟 ｜4 分

**① 剔掉散客会损失多少营业额？**

最简算法：**两级金额相减**（不用写新 SQL，用 Q15 的两个数）

| 口径 | 金额 |
|---|---|
| 剔退货 + 剔非正价 + 去重（**保留**散客） | **20,476,260.45** |
| 清洗后（**剔掉**散客）= retail_clean | **17,374,804.27** |
| **散客损失 = 两者之差** | **3,101,456.18** |

占"有效正向流水"的比例 = 3,101,456.18 ÷ 20,476,260.45 = **15.15%**

（涉及 **228,488 行**散客记录被剔掉：1,007,913 − 779,425，占该口径行数的 **22.67%**。）

**② 不剔会怎样？**

散客没有 ID，**每次购买都会被当成一个新客户**。后果：

- 客户总数虚高（5,942 → 会膨胀到十几万量级）
- **复购率、留存率被系统性低估** —— 因为同一个散客的第二次购买，永远不会和第一次关联上
- RFM 分层彻底失效（F 永远等于 1）

**③ 怎么在作品集里交代？**

> "本分析剔除了 22.8% 的无客户 ID 记录（占有效正向流水 15.2%）。这些是匿名散客，无法做客户级追踪。因此本报告的留存率、复购率**仅代表有账号客户**，绝对水平会低于全量口径；但**趋势和相对比较仍然成立**。"

**判分**：算出 3,101,456.18 得 2 分；② 或 ③ 能说清"会破坏什么"再得 2 分。

**这题真正考的**：面试官想看的是 **你知道这个取舍有代价，而且说得出代价是什么**。最差的回答是"反正老师说要剔我就剔了"。最好的回答是第 ③ 条那种 —— 主动承认口径局限。

### Q18 · RANK 客户消费榜 ｜★★★｜10 分钟 ｜3 分

```sql
SELECT customer_id,
       ROUND(SUM(amount), 2)      AS revenue,
       COUNT(DISTINCT invoice)    AS orders,
       RANK() OVER (ORDER BY SUM(amount) DESC) AS rnk
FROM retail_clean
GROUP BY customer_id
ORDER BY revenue DESC
LIMIT 20;
```

**标准答案（Top 10）**

| 排名 | customer_id | 流水 | 订单数 |
|---|---|---|---|
| 1 | **18102** | **580,987.04** | 145 |
| 2 | **14646** | **528,602.52** | 151 |
| 3 | 14156 | 313,437.62 | 156 |
| 4 | 14911 | 291,420.81 | **398** |
| 5 | 17450 | 244,784.25 | 51 |
| 6 | 13694 | 195,640.69 | 143 |
| 7 | 17511 | 172,132.87 | 60 |
| 8 | **16446** | **168,472.50** | **2** ⚠️ |
| 9 | 16684 | 147,142.77 | 55 |
| 10 | 12415 | 144,458.37 | 28 |

**三种排名函数的区别（必答）**

| 函数 | 平局时 | 例（金额 100/100/90） |
|---|---|---|
| `ROW_NUMBER` | 强行分先后 | 1, 2, 3 |
| `RANK` | 跳号 | **1, 1, 3** |
| `DENSE_RANK` | 不跳号 | 1, 1, 2 |

**这题真正的洞察**：客户 **16446 只下过 2 单，却排到第 8 名（168,472.50）** —— 因为其中一单就是那笔 8 万件 `PAPER CRAFT, LITTLE BIRDIE` 的超级大单。而客户 **14911 下了 398 单只排第 4**，是高频小单客户。

> **这就是"客户价值结构"的雏形**：一种是**单笔巨额**（16446），一种是**高频复购**（14911），一种是**长期稳定**（18102 从数据第一天买到最后一天）。**三类客户要用三种完全不同的运营策略。**

**判分**：Top 10 对上 3 分。

### Q20 · CTE 同期群留存矩阵 ｜★★★★★｜20 分钟 ｜6 分

```sql
WITH first_order AS (
  SELECT customer_id,
         DATE_FORMAT(MIN(invoice_date), '%Y-%m') AS cohort_m
  FROM retail_clean
  GROUP BY customer_id
),
activity AS (
  SELECT DISTINCT customer_id,
         DATE_FORMAT(invoice_date, '%Y-%m') AS act_m
  FROM retail_clean
),
j AS (
  SELECT f.customer_id,
         f.cohort_m,
         PERIOD_DIFF(REPLACE(a.act_m, '-', ''), REPLACE(f.cohort_m, '-', '')) AS m_idx
  FROM first_order f
  JOIN activity a ON a.customer_id = f.customer_id
)
SELECT cohort_m,
       COUNT(DISTINCT IF(m_idx = 0, customer_id, NULL)) AS m0,
       COUNT(DISTINCT IF(m_idx = 1, customer_id, NULL)) AS m1,
       COUNT(DISTINCT IF(m_idx = 2, customer_id, NULL)) AS m2,
       COUNT(DISTINCT IF(m_idx = 3, customer_id, NULL)) AS m3,
       COUNT(DISTINCT IF(m_idx = 4, customer_id, NULL)) AS m4,
       COUNT(DISTINCT IF(m_idx = 5, customer_id, NULL)) AS m5,
       COUNT(DISTINCT IF(m_idx = 6, customer_id, NULL)) AS m6
FROM j
GROUP BY cohort_m
ORDER BY cohort_m;
```

**标准答案（前 6 个同期群）**

| 同期群 | 新增客户 M0 | M1 | M2 | M3 | M4 | M5 | M6 |
|---|---|---|---|---|---|---|---|
| 2009-12 | 955 | 337 | 319 | 406 | 363 | 343 | 360 |
| 2010-01 | 383 | 79 | 119 | 117 | 101 | 115 | 99 |
| 2010-02 | 374 | 89 | 84 | 109 | 92 | 75 | 72 |
| 2010-03 | 443 | 84 | 102 | 107 | 103 | 90 | 109 |
| 2010-04 | 294 | 57 | 57 | 48 | 54 | 66 | 81 |
| 2010-05 | 254 | 40 | 43 | 44 | 45 | 65 | 54 |

**换算成留存率（除以 M0），以 2010-01 群为例**

| M1 | M2 | M3 | M4 | M5 | M6 |
|---|---|---|---|---|---|
| **20.6%** | 31.1% | 30.5% | 26.4% | 30.0% | 25.8% |

**❗ 两个必须能解释的现象**

1. **M1（20.6%）比 M2、M3 都低。** 正常留存曲线应该单调下降。出现"次月留存低于第三月"，通常是**观察窗口不够长**造成的 —— 同一批客户里，有些人第一单是月末下的，第二单自然落在两个月后。这是 cohort 分析的固有特性，不是数据错误。
2. **越靠后的同期群，右边的格子越小甚至为 0**（比如 2011-11 群只有 M0/M1 有值）。因为数据 2011-12-09 就截止了 —— **格子为 0 不代表客户流失，是没有观察窗口**。矩阵右下角必须留空，不能填 0。

**判分（6 分）**：三个 CTE 结构正确 3 分；矩阵跑出来 5 分；**能解释 M1 < M2 得 6 分**（这一条是面试加分题）。

**坑**：`PERIOD_DIFF` 参数是 `YYMM` 或 `YYYYMM` 的**数字字符串**，所以要先 `REPLACE(x, '-', '')` 把 `2010-01` 变成 `201001`。

### Q25 · RFM 原始值 ｜★★★｜12 分钟 ｜3 分

```sql
SELECT customer_id,
       DATEDIFF('2011-12-09', MAX(invoice_date)) AS recency_days,
       COUNT(DISTINCT invoice)                   AS frequency,
       ROUND(SUM(amount), 2)                     AS monetary
FROM retail_clean
GROUP BY customer_id
ORDER BY monetary DESC
LIMIT 10;
```

**标准答案（Top 10，按 M 排序）**

| customer_id | R（天） | F（单数） | M（金额） |
|---|---|---|---|
| 18102 | 0 | 145 | 580,987.04 |
| 14646 | **1** | 151 | 528,602.52 |
| 14156 | **9** | 156 | 313,437.62 |
| 14911 | **1** | 398 | 291,420.81 |
| 17450 | **8** | 51 | 244,784.25 |
| 13694 | **3** | 143 | 195,640.69 |
| 17511 | **2** | 60 | 172,132.87 |
| **16446** | **0** | **2** | **168,472.50** |
| 16684 | **4** | 55 | 147,142.77 |
| 12415 | **24** | 28 | 144,458.37 |

**判分**：三个指标都算对 3 分。

**三个必须注意的点**

1. **R 的基准日不能写 `NOW()`** —— 数据截止 2011-12-09，用今天做基准，所有人的 R 都是 5000 多天，RFM 分层全废。**必须用数据的 `MAX(invoice_date)`。**
2. 更严谨的写法是动态取：
   ```sql
   SET @snapshot := (SELECT MAX(invoice_date) FROM retail_clean);
   ```
   然后用 `DATEDIFF(@snapshot, MAX(invoice_date))`。**这样数据更新后脚本不用改。**
3. **`R = 0` 的人不是"今天来的"** —— 是因为他们的最后一单就下在数据截止日 2011-12-09。这一列的业务含义是"距快照日多少天没下单"，不是"距今天"。
4. **`DATEDIFF` 会忽略时分秒**：客户 14646 的最后一单是 2011-12-08 的某一刻，`DATEDIFF('2011-12-09', 2011-12-08 xx:xx)` = **1 天**，不是 0 天。
   如果你用"精确到秒的差再取整"去算，这一列会整体偏小 1 天（14646 会算成 0、14156 会算成 8）。
   两种口径都对，**但 R 值直接决定 RFM 分箱，所以 Day 8 做分层前必须先把这个口径固定下来。**

**下一步（Day 8 会用到）**：把 R/F/M 各自按分位数切成 1~5 分，再组合成 RFM 分群（重要价值客户 / 一般保持客户 / 流失预警客户等 8 类）。

### Q26 · 商业结论（主观）｜★★★★★｜20 分钟 ｜3 分

**没有标准答案，但有好坏之分。** 下面是满分答案的示范（数字全部来自前面各题）：

> **① 钱从哪来？**
> 这是一家**高度依赖英国本土市场（82.82%）的在线礼品批发商**，收入有明显的**圣诞季节性**（9~11 月连续两年走高，11 月见顶 116 万）。客户结构极度集中 —— **4.4% 的客户贡献了 50% 的流水**，最大客户 18102 贡献 58.1 万、横跨全数据周期（2009-12-01 ~ 2011-12-09，145 单）。
>
> **② 最大风险？**
> **单市场 + 单客户双重集中。** 英国占 82.82%，一旦英国零售环境或汇率变化，八成收入直接受影响；同时爱尔兰市场仅 5 个客户就贡献 61.7 万（3.55%），任何一个大客户流失都会造成断崖式下跌。次要风险是**客单价微降**（2011-11 客单 435.15，低于 2010-11 的 450.89；订单数反而多了 70 单）。
>
> **③ 数据本身有什么坑（这一条最加分）？**
> 我把两份数据合并时发现 **34,335 行完全重复** —— 因为两份数据的时间范围在 2010-12-01~12-09 重叠了 9 天。如果不去重，2010 年 12 月的流水会虚高 55.08%（884,591.89 vs 正确的 570,422.73）。另外两个 12 月天数都不完整（2010-12 到 12-23、2011-12 只到 12-09），**不能直接参与环比**；换成同口径（12 月 1–9 日）其实是同比 **+66.49%**。
>
> **④ 下一步先做什么分析？**
> **先做客户流失预警** —— 基于 RFM 找出"曾经是大客户、但最近 90 天没下单"的名单（用 Q25 的 R 值筛），这批人的挽回成本远低于拉新。其次验证客单价下滑的原因：是商品结构变了（利润款占比下降），还是给了更多折扣。

**判分（3 分）**

| 给分点 | 说明 |
|---|---|
| 每句话里**至少一个具体数字** | 形容词（"很大""很高"）不给分 |
| 风险要**用数字支撑** | 说"集中在英国"是常识；说"英国占 82.82%"才是分析 |
| 下一步要**具体可执行** | "再深入分析"不给分；"筛出 R>90 天的大客户做挽回"给分 |
| **主动交代数据局限** | 重复行、残月、散客口径 —— 说出来就是加分 |
